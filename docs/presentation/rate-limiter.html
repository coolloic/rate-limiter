Request flow of one check

Algorithm

Why a sliding window log

Algorithm Holds “≤ 10 in any second”? Memory / consumer Wait time
Fixed window (counter per whole second) No: 20 in 20 ms at a boundary O(1) Coarse (to boundary)
Token bucket (10 tokens, 10/s refill) No: up to ~19 in a rolling second O(1) Exact next token
Sliding window log (chosen) Yes, exactly, by construction O(limit): ≤ 10 numbers Exact: oldest + 1000 − now

Algorithm

Sliding window log, step by step

consume(key, { limit, windowMs }) {
  const now = this.clock.now();
  return this.store.update(key, windowMs, (previous = []) => {
    const live = previous.filter((t) => t > now - windowMs); // 1
    if (live.length < limit) {                                // 2
      const state = [...live, now];
      return { state, result: { allowed: true,
        remaining: limit - state.length, ... } };
    }
    const waitMs = live[0] + windowMs - now;                  // 3
    return { state: live,     // denied: not recorded
      result: { allowed: false, retryAfterMs: waitMs, ... } };
  });
}

Simplified from src/strategies/SlidingWindowLogStrategy.ts

  • 1. Drop timestamps ≤ now − windowMs
  • 2. Allow + record now if under the limit
  • 3. Deny with the exact wait until the oldest leaves
  • Denied requests are not recorded: hammering never pushes the wait out
  • The log never holds more than limit timestamps (asserted)
  • Atomic: InMemoryStore reads, transitions and writes with no await in between
Test, 10 per 1000 ms: 5 at t=0 and 5 at t=500 → t=999 denied, retryAfterMs: 1 → at t=1000 exactly 5 slots free; the 6th is denied with retryAfterMs: 500.

Extension (a) · built

Limits per resource and per consumer

Most specific rule wins:

createRateLimiter({
  policies: new ConfigurablePolicyResolver({
    default:   { limit: 10, windowMs: 1000 },
    resources: { search: { limit: 5, windowMs: 1000 } },
    consumers: { 'partner-acme': { limit: 100, windowMs: 1000 } },
    overrides: { search: { 'partner-acme': { limit: 50, ... } } },
  }),
});
  • Validated up front: InvalidArgumentError, e.g. overrides.search.partner-acme.limit must be a positive integer, got 0 (a zero limit would mean zero-wait denies and a spinning client)
  • Collision-proof keys: JSON.stringify([resource, consumerId]), so ["a:b","c"] ≠ ["a","b:c"]
  • Own-property lookups: IDs such as "__proto__" or "toString" are safe
  • Missing resource → DEFAULT_RESOURCE ("default")

Integration

HTTP headers and client-side waiting

Server: toRateLimitHeaders(result)

Header Value
RateLimit-Limit Quota per window
RateLimit-Remaining Units left
RateLimit-Reset Relative seconds until a unit frees up
Retry-After Only on deny (RFC 9110)
  • IETF RateLimit header fields draft
  • Seconds rounded up: 1 ms → 1, 1000 ms → 1, 1001 ms → 2, so an obedient client is never early
  • The request using the last unit is allowed with remaining: 0, no Retry-After

Client: acquire / withRateLimit

await acquire(limiter, { consumerId: 'nightly-job' }, {
  maxWaitMs: 5000, jitterMs: 50,
  signal: AbortSignal.timeout(10_000),
});
const throttled =
  withRateLimit(limiter, consumer, callApi);
  • Waits the exact retryAfterMs, not exponential backoff
  • jitterMs adds 0..jitter on top: spread out, never early
  • maxWaitMs / maxAttempts: fail fast with RateLimitTimeoutError, without sleeping first
  • signal aborts at once; invalid options → InvalidArgumentError
  • Ideas from urllib3.Retry, tenacity, p-limit

Extension (b) · designed, not built

High availability: shared state in Redis

Plug-in options

  • RedisStore behind RateLimitStore, atomic via WATCH/MULTI retries
  • Simpler: a Redis RateLimitStrategy running one Lua script (ZREMRANGEBYSCORE, ZCARD, ZADD, PEXPIRE)

Correctness

  • One script = atomic check-and-record: no two instances take the last slot
  • Redis TIME: app clock skew doesn't matter
  • Cluster: hash tags rl:{consumerId}:… for multi-key checks

Failure policy

  • Fail-open keeps serving, drops the limit; fail-closed turns a Redis outage into an outage
  • Middle ground: short timeout → local limit / N + circuit breaker

Operations

  • Async replication: failover may briefly over-allow; documented
  • Local pre-check denies clearly-over consumers without a round trip
  • API is already async: callers don't change

Summary

Takeaways

  • Correct by construction: a sliding window log holds “≤ 10 in any second”, proven by a randomised invariant test
  • Exact answers: retryAfterMs to the millisecond; headers rounded up; denied requests never recorded
  • Extensible: Strategy, Adapter, Factory and Decorator seams; per-resource / per-consumer limits built
  • Ready to scale out: async API and store port prepared for Redis (Lua, TIME, explicit failure policy)
  • Disciplined delivery: OOAD → plan → TDD → review → one small PR per task
